## 問題與詞義

使用者要求回頭核對最初規劃，指出看不到「縱深跟橫向遷移變化」。本輪先用以下工作定義審查；不聲稱使用者已確認這兩個詞的精確定義：

- 縱深：沿 migration 順序，看同一表／欄位如何變化，以及各變化的來源與可信狀態。
- 橫向：在同一份 migration 中，看哪些表、欄位與明確外鍵一起發生變化。

這是閱讀維度，不是 Git／資料庫分支，也不是畫面一定要橫排或一定要動畫。

## 原始目標、歷史候選與核准範圍

[決策索引](../DECISIONS.zh-TW.md) 的產品目標是讓使用者理解資料庫如何由 migrations 演化到目前結構。早期 Table／Column History、Timeline、Semantic Zoom 被記為候選，沒有因此成為已核准需求；完整逐字原討論已不在公開 clone，不能聲稱本輪重新讀過全文。

[A-01](A-01-positioning-report.zh-TW.md) 記錄使用者同意「看懂專案結構」及「看懂單次變更」雙目標，候選分析仍為 draft。[R7](R7-workspace-reading.zh-TW.md) 的 A 則明確核准同一工作區、順序導航、固定選表與來源返回，排除 history DTO、時間軸與任意兩時點比較。

因此 R7 的 done 可以代表核准批次已交付，不能直接代表整個「理解演變」產品目標已充分達成。本輪沒有證據顯示開發端漏做已核准的完整歷程功能；落差首先在研究規劃把線性閱讀收斂為逐份切換，驗收主要檢查操作與資料一致性，沒有充分定義整段演變應如何被理解。

## 修訂 2：最實際的變更閱讀例子

既有自撰 commerce 的 `2026_10_04_000002_create_products.php` 定義 `price` 為 `decimal(8,2)`；`2026_10_04_000007_price_change.php` 明確改成 `decimal(10,2)->nullable()->default(0)->change()`。

目前主要標籤為 `changeColumn · products.price (decimal)` 與 `columnChanged · products.price`；圖投影只含 name／type／nullable／PK／FK，precision／scale／default 不在列文字中。完整 DTO 與右側屬性有資料，但需要另外查閱再自己對照。候選驗收應要求看出 decimal 參數 8,2→10,2、變為 nullable、加 default(0)，來源仍能返回；不宣稱實際 DB 修改可執行。

這個例子與前節的 nickname 新增／移除、同檔 users／posts 外鍵調整共同涵蓋「屬性、跨步、跨表」三種閱讀問題，避免只拿改表名或大幅改造來論證需求。全部是既有 fixture，沒有假稱外部使用者需求研究。
