## 問題與詞義

使用者要求回頭核對最初規劃，指出看不到「縱深跟橫向遷移變化」。本輪先用以下工作定義審查；不聲稱使用者已確認這兩個詞的精確定義：

- 縱深：沿 migration 順序，看同一表／欄位如何變化，以及各變化的來源與可信狀態。
- 橫向：在同一份 migration 中，看哪些表、欄位與明確外鍵一起發生變化。

這是閱讀維度，不是 Git／資料庫分支，也不是畫面一定要橫排或一定要動畫。

## 原始目標、歷史候選與核准範圍

[決策索引](../DECISIONS.zh-TW.md) 的產品目標是讓使用者理解資料庫如何由 migrations 演化到目前結構。早期 Table／Column History、Timeline、Semantic Zoom 被記為候選，沒有因此成為已核准需求；完整逐字原討論已不在公開 clone，不能聲稱本輪重新讀過全文。

[A-01](A-01-positioning-report.zh-TW.md) 記錄使用者同意「看懂專案結構」及「看懂單次變更」雙目標，候選分析仍為 draft。[R7](R7-workspace-reading.zh-TW.md) 的 A 則明確核准同一工作區、順序導航、固定選表與來源返回，排除 history DTO、時間軸與任意兩時點比較。

因此 R7 的 done 可以代表核准批次已交付，不能直接代表整個「理解演變」產品目標已充分達成。本輪沒有證據顯示開發端漏做已核准的完整歷程功能；落差首先在研究規劃把線性閱讀收斂為逐份切換，驗收主要檢查操作與資料一致性，沒有充分定義整段演變應如何被理解。

## 現行能力與落差證據

| 維度 | 現行能力 | 尚未提供／呈現限制 | 原始碼證據 |
|---|---|---|---|
| 縱深 | 前／下一份、保留 literal 表名；R4 依完整順序列出名稱涉及的操作與來源 | 來源清單不等於整段結構變化摘要；明細「本次變更」只取當前 step；使用者仍須逐份切換，整合前後狀態 | `ProjectResults.tsx`、`WorkspaceDetails.tsx`、`OperationSources.tsx`、`operation-sources.ts` |
| 橫向 | 一份 migration 的真實 before／after ERD、diff 色彩／標記、涉及物件及差異清單 | 兩圖由 `SchemaComparison` 依序呈現；摘要在圖後方；沒有將跨表改動整理為單一緊湊的閱讀總覽 | `SchemaComparison.tsx`、`MigrationReading.tsx` |
| 連續觀察 | 換步驟保留選表；同一次比較共用圖形 view | `SchemaSnapshots` 以快照 id 為 key 重新建立圖，換步驟可重設位置／縮放；不保證連續視覺追蹤 | `SchemaSnapshots.tsx`；[M42 限制](../milestone-42.zh-TW.md) |

以上不能說成「完全沒有變更視覺化」；也不能因為 DTO 與按鈕都有，就推論讀者能直接掌握全段變化。本輪沒有即時線上 DOM／截圖可讀工具；ambient URL 不代表已看過畫面。結論是來源與規格審查，沒有執行程式、測試或真人可用性測試。

## 具體任務與可查例子

以下都是 repo 既有自撰 fixture，不是外部真實需求證據，也不是新增驗收已通過的聲明。

1. `project/`：第二份新增 `users.nickname`，第三份移除。縱深任務是直接回答「在哪兩份變更、各自新增或移除、當時是否生效、來源在哪」，而不只證明按下一份後欄位真的不見。
2. 同一 fixture 的 `display_name`：第二份由明確 rename 得到；第三份 drop 後同名重建、長度 200 且 nullable。不能把同名重建說成 changeColumn 或連續穩定身分。
3. `foreign-keys/2026_03_03_000000_revise_keys.php`：同檔將 `users.id` 改名為 `user_key`、`posts.user_id` 改名為 `author_id`，移除舊外鍵並新增指向 `users.user_key` 的外鍵。橫向任務是共同呈現這些明確操作及實際結構差異，不推測業務影響或 DB 執行安全性。

## 候選方案與取捨

| 候選 | 範圍 | 取捨 |

| 維持逐份閱讀、改善既有入口 | 更清楚說明前後比較、來源清單與目前步驟 | 成本較低；仍把整段整合工作留給讀者 |

| 完整歷程身分模型／動畫時間軸 | 新增跨時點身分與更多互動能力 | 明顯擴大歷史排除範圍；本次不足以證明必要性，不自動納入 |

## 方向、範圍與排除

本次方向是明確承認並保存「操作批次 done，不等於產品閱讀目標完成」的落差。後續若調整設計，先用上述具體任務展示內容與狀態，再決定範圍；此方向與候選畫面均未獲功能核准。

core 像分析 service，已回傳逐份 before／after／diff 與操作 DTO；目前畫面主要逐份選取它們。整合閱讀視圖是另一個產品決策，不能直接假設要新增 Laravel service、解析 model、改公開 DTO 或另寫 replay。

排除：實作、修改測試／設定／scripts／workflow、安裝、執行專案、部署、排程、下載落盤、推測未知 schema、跨 rename 身分及將候選自動轉 approved。R7 done 不回退，A-04／A-05 不因此核准。
